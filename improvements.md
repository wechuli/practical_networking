## Overall Assessment

**The course is broad and relevant, but it is not yet a fully reliable, comprehensive practical course as written.** It is a substantial Linux-centric networking foundation with useful diagrams, worked calculations, CLI examples, and production-oriented topics. Much of that material should stay. The main work is correcting mechanisms, making the labs reproduce their stated outcomes safely, and completing the practical objectives already promised, not adding more introductory prose.

**It cannot currently be described as free of made-up or unsupported information.** There are confirmed incorrect reference titles and a nonexistent command, as well as invented-looking numerical guarantees and examples that contradict their own setup. That does not establish deliberate fabrication or make all the material untrustworthy. Synthetic examples are legitimate teaching tools, but must be labeled as synthetic, technically coherent, and separate from sourced historical incidents or actual captured output.

**Practical recommendation:** retain the course structure and adequate explanations; resolve P0 and P1 findings before presenting affected labs as copy-and-run; then complete and assess the missing core outcomes. Treat "mastery" as a demonstrated ability to diagnose unfamiliar failures with evidence, not as a consequence of reading all modules.

## Scope and Standard

The review covers [networking_course_outline.md](networking_course_outline.md) and all 25 module documents, including their objectives, diagrams, examples, labs, scenarios, summaries, and references. The original note-generation requirements (not part of this repository) provide an additional quality benchmark: factual mechanisms, visual explanations, exact lab commands, observable verification, and production relevance. The original repository's `script.sh` (not part of this repository) was inspected only to establish whether it supplied a missing lab harness; it contains personal provisioning/command notes, not a complete course test harness. The generated PDF and legacy source examples were not independently audited.

The review distinguishes factual errors, lab reproducibility or safety problems, and material gaps in the stated learning outcomes. Adequately explained material does not need expansion simply to make the course longer. Public protocol standards and official product documentation are used to check disputed claims.

## Outline and Module Consistency

- **Correction: MTU is not the complete Ethernet frame size.** The [outline's MTU definition](networking_course_outline.md) calls MTU the largest frame on a link. The [detailed explanation in Module 14](modules/module-14-network-performance.md) correctly measures the IP packet, excluding the Ethernet header and trailer. Align the outline with that explanation; a 1500-byte Ethernet IP MTU is not a 1500-byte Ethernet frame. This is a correction to the outline, not a request to rewrite the sound explanation in the module.
- **Correct other abbreviated statements too.** The outline repeats the [13 root IPs claim](networking_course_outline.md), [ECDHE-only forward secrecy](networking_course_outline.md), [CRLs replaced by OCSP](networking_course_outline.md), and [one HTTP/1.1 request per connection](networking_course_outline.md). Apply the same qualifications recommended for the owning modules, so a learner does not memorize an incorrect summary after reading a better explanation.
- **Reconcile Docker and diagnostic summaries.** [Container-name resolution](networking_course_outline.md) is not generally a hosts-file mechanism on user-defined Docker networks. [Packet captures](networking_course_outline.md) have observation limits, and [Connection Refused](networking_course_outline.md) does not establish that something is listening. The outline should preserve these distinctions.
- **Track promised deliverables.** The [NTP security objective](networking_course_outline.md) is absent from Module 23. The outline's gRPC, Ingress, Linkerd/mTLS, flow-log, and tracing exercises also need concrete implementations, as described in their module reviews. The [appendices](networking_course_outline.md) are topic lists, not completed reference appendices; either supply them or link each item to the adequate existing module reference card. Update the [Azure flow-log topic](networking_course_outline.md) to its supported successor for new setups.

## Course-Wide Improvements

### Required for Practical Completion

1. **Publish a tested lab contract.** Specify supported Ubuntu/kernel, Docker/firewall backend, Kubernetes/CNI, curl/TLS backend, OpenSSL, Python, and library versions. Check required commands and capabilities before each exercise. Use a Python virtual environment where packages are needed. Identify local-only, second-host, browser, and optional cloud requirements, including permissions and potential cost. "Ubuntu 22.04+" by itself does not guarantee compatible feature sets.
2. **Contain failure injection and guarantee cleanup.** Keep firewall, packet-loss, MTU, routing, and resource-limit changes inside lab-owned namespaces or disposable VMs. Save actual original settings, use unique resource names, stop owned processes before deleting namespaces, and restore state on interruption or failure. Do not flush host-wide rules, change a management interface, expose the entire temporary directory with an HTTP server, or stop unrelated processes as routine lab work.
3. **Make verification discriminate.** Every fault lab should show a healthy baseline, the intended failure, evidence supporting the cause, one plausible alternative rejected, a minimal repair, and restored behavior. Test security controls with both allowed and denied traffic. Check command exit status, nonempty captures, expected protocol fields, and readiness before printing success. Avoid suppressing errors that a learner needs to diagnose setup failure.
4. **Separate invariants from illustrative output.** A SYN flag, a matched DNS transaction, and verified certificate rejection can be required observations. Exact public IPs, certificate issuers, hop counts, RTTs, retransmission counts, and container addresses are not stable expected output. Label transcripts as captured with date/version or explicitly illustrative. Packetization and offload behavior must not be mistaken for guaranteed packet boundaries.
5. **Complete the missing operational exercises.** Prioritize an actual IPv6 control-plane lab, controlled authoritative/recursive DNS caching, correct PMTUD, concurrent HTTP/2, a runnable gRPC service, maintained Ingress/Gateway routing, mesh mTLS verification, flow-log analysis, and a propagated multi-service trace. These support existing claims rather than expanding the course into unrelated specialties.
6. **Keep one canonical explanation per concept.** MTU/MSS, TLS guarantees, TIME_WAIT, DNS caching, and capture interpretation recur throughout the course. Fix the owning explanation and align the outline, diagrams, scenarios, and quick-reference cards. Cross-link rather than repeat long prose; some of the best explanations already exist elsewhere in the course.
7. **Replace unsourced rankings with qualified evidence.** Claims such as DNS being the number-one incident cause, TLS being number two, a method eliminating exactly 80% of debugging, guaranteed performance multipliers, and all providers using one topology need evidence or removal. Source real incidents individually. Keep product limits and lifecycle claims dated, and distinguish current specifications from historical references.
8. **Assess outcomes, not command copying.** Provide a learner-facing challenge and separate solution. Require a short incident report with the affected flow, timestamps, relevant packets/counters, rejected alternatives, fix, and cleanup evidence. Preserve a small set of sanitized captures/logs or deterministic generators so assessment does not depend entirely on live public services.

### Additional Depth by Audience

These are valuable extensions after correctness and promised labs are addressed, not reasons to rewrite sufficient material:

- **Physical-network support:** a small VLAN access/trunk/tagging and STP/loop-prevention exercise, plus link-error/duplex counters. VLAN/STP vocabulary appears, but practical treatment is thin for learners diagnosing LANs. Wireless RF engineering can remain outside a Linux/cloud-focused core.
- **Application developers:** a short request lifecycle spanning pool acquisition, DNS, connect, TLS, write/read, and total deadline; distinguish TCP keepalive from HTTP persistence and application heartbeats. Add bounded retry/backoff and idempotency guidance, Nagle/delayed-ACK interaction, and a proxy CONNECT/NO_PROXY/TLS-interception example.
- **Performance specialists:** an ECN/AQM/bufferbloat comparison and endpoint CPU/NIC/queue/packet-rate checks. Avoid concluding that any low throughput must be a TCP-buffer problem.
- **Cloud/platform engineers:** one complete private-service access example including peering/transit, overlapping prefixes, private endpoint DNS, effective routes, policy, and return path. Add a source-preservation/draining exercise for long-lived HTTP/2 or gRPC connections and a small ECMP/reverse-path-filtering example.

Deep MPLS/EVPN design, full routing-vendor configuration, specialist Wi-Fi engineering, and cryptographic implementation are not necessary to meet the stated audience's core needs. A scoped practical course can be comprehensive without covering every networking specialty.

### Suggested Acceptance Criteria

- All P0 safety/security demonstrations and P1 correctness defects are resolved, including duplicated outline/summary claims.
- Every required lab runs from a clean supported environment, reaches its stated observable result, and leaves that environment clean; an interrupted run also restores its changes.
- Each advertised learning objective maps to an explanation and an appropriate exercise or assessment. Conceptual history does not need an artificial packet lab.
- At least one new learner can diagnose each capstone without reading its solution, justify the result with evidence, and preserve intended access restrictions after the fix.
- Source references match their titles and claims; current product features/defaults are dated. All example-only transcripts are labeled, and time estimates are checked with a pilot learner.

## Module-by-Module Findings

### Module 00: Before We Begin

**Keep:** The tool-to-protocol mapping, layered vocabulary, and emphasis on observing traffic are appropriate for an introduction.

- **Accuracy:** Qualify the [five-step model](modules/module-00-before-we-begin.md) as a fresh HTTPS-over-TCP example. Cached DNS, existing connections, plaintext protocols, and QUIC do not universally follow it. A timeout can occur during connection establishment or an established transfer; it does not prove that Step 2 failed. Remove the unsupported claim that this classification eliminates exactly 80% of the diagnostic space.
- **Practicality:** The [environment setup](modules/module-00-before-we-begin.md) does not yet establish the promised environment for every exercise. Later labs need additional software, local services, cloud accounts, and a Kubernetes CNI that actually enforces NetworkPolicy. Provide a versioned prerequisite checklist and preflight checks, distinguish optional cloud exercises, and explain that Docker group membership is effectively root access. Replace the blanket instruction to run every displayed command with an explicit distinction between inspection commands and lab-only disruptive examples.

### Module 01: History of Networking

**Keep:** Packet switching versus circuit switching and the practical value of reading standards need no substantial expansion.

- **Accuracy:** Repair the [timeline](modules/module-01-history-of-networking.md): RFCs 1034/1035 are from 1987, not 1984; earlier DNS specifications are RFCs 882/883 from 1983. HTTP/3 RFC 9114 is from 2022, not 2021. TLS 1.3 did not make correctly configured TLS 1.2 unusable, and RFC 9293 consolidated numerous intervening TCP updates rather than being the first TCP change in forty years. Do not assign the exact modern 1500-byte Ethernet limit to the 1973 invention without a historical source. Explain that not every RFC is an Internet Standard and that documents can update, not only obsolete, earlier RFCs.
- **Accuracy:** In [Common Failure Patterns](modules/module-01-history-of-networking.md), `169.254.x.x` is IPv4 link-local, not IPv6; `dig` does not consult the hosts file; and a large TIME_WAIT count alone does not establish ephemeral-port exhaustion. Distinguish the largest port number, 65535, from 65536 possible 16-bit values and the much smaller configured ephemeral range.
- **Precision:** Modern switched Ethernet links are commonly point-to-point; that does not guarantee an uncontended end-to-end service. Cloud subnets should not be presented as ordinary Ethernet broadcast domains. Source or qualify the ARPANET survivability narrative instead of turning a simplified historical motivation into a protocol fact.

### Module 02: Quickstart - A Webpage End to End

**Keep:** The annotated curl walkthrough is useful and appropriately placed before the protocol deep dives.

- **Accuracy:** Correct the [teardown diagram](modules/module-02-quickstart-a-webpage-end-to-end.md): the separate acknowledgment of a FIN is an ACK, not an additional FIN followed by another FIN from the same side. Show either a four-segment close or a combined FIN+ACK close. Qualify "no phase can be skipped" and distinguish TLS session resumption from reuse of an already-open connection. Disabling the browser HTTP cache does not flush DNS or force fresh TCP/TLS handshakes.
- **Lab reliability:** The [capture exercise](modules/module-02-quickstart-a-webpage-end-to-end.md) selects one IPv4 address, but curl independently resolves the hostname and can choose another address or IPv6. Pin the request to the captured address while preserving the hostname, or capture the actual chosen endpoint. Avoid the earlier hard-coded historical address for example.com. Packet length and PSH flags are not sufficient to identify a TLS Certificate message; teach dissector-based identification and the limits of observing encrypted TLS 1.3.
- **Measurement:** TTFB includes network travel as well as server work and starts with the first response byte, not necessarily the response body. Browser initial-connection timing may include TLS, so adding displayed rows can double-count. A second `dig` still incurs process startup and the trip to a remote resolver; neither near-zero duration nor a full cold DNS walk is guaranteed. Grade phase interpretation, not specific public-site timings or the mandatory presence of every timing row.

### Module 03: Networking Fundamentals

**Keep:** The interface, route, and neighbor inspection sequence and basic device comparisons are useful. The vocabulary does not need another general introduction.

- **Accuracy:** Correct [MTU](modules/module-03-networking-fundamentals.md) and [BDP](modules/module-03-networking-fundamentals.md) consistently with Module 14. BDP describes the in-flight data needed to fill the path, not the maximum TCP can have outstanding. A difference between iperf3 TCP sender and receiver summaries is not sufficient proof of packet loss; account for measurement intervals and use retransmission evidence.
- **Accuracy:** In [MAC-address learning](modules/module-03-networking-fundamentals.md), a switch learns from the source MAC of incoming frames, not specifically from a response to flooding. Unknown unicast flooding is normal, not inherently a network failure. Locally administered and randomized MACs do not encode a guaranteed manufacturer OUI, Docker does not universally use one fixed prefix, and not every interface has an Ethernet MAC. Qualify the claim that all virtual interfaces show UNKNOWN.
- **Diagnosis:** A STALE neighbor remains usable while reachability is checked; it need not be resolved before the first packet can be sent. No default route does not prevent use of more-specific off-link routes. An interface without IPv4 may intentionally be unnumbered or IPv6-only. In the [measurement exercise](modules/module-03-networking-fundamentals.md), pinging a public resolver and running iperf3 to another host cannot confirm a BDP bottleneck. Measure the same path and inspect the limiting window. Stop only the test's own iperf3 process.
- **Diagram:** Redraw the spine-leaf example so every leaf connects to every spine, without implying that a spine-to-spine link is required. Clarify whether hop counts mean links or forwarding devices; same-leaf and cross-leaf traffic do not traverse the same number of switches. Do not attribute a provider's unspecified AZ impairment to a particular physical component without evidence.

### Module 04: The OSI Model

**Keep:** Encapsulation and the acknowledgment that real protocols do not fit OSI perfectly are well explained.

- **Diagnostic accuracy:** The [bottom-up checklist and scenarios](modules/module-04-the-osi-model.md) overstate what ping proves. Failed ICMP does not require stopping TCP/application investigation; successful ICMP does not eliminate protocol-specific ACLs, size-dependent loss, or different paths. Treat the layer model as an organizing aid, not a mandatory order. In particular, replace the RDS example's expected successful ping: RDS does not accept ICMP, so test the database TCP endpoint. A refused connection also need not prove the actual server generated the refusal.
- **Capture blocker:** [Lab Part 1](modules/module-04-the-osi-model.md) captures on Linux `any` but expects Ethernet II source/destination headers. That normally produces Linux cooked capture, not a complete Ethernet header. Select the actual interface when teaching Ethernet bytes, resolve and pin the endpoint before starting capture, and explain that Wireshark's Frame entry is capture metadata, not captured Layer 1 signals. The SYN-or-ACK filter matches far more than the handshake.
- **Precision:** Distinguish a protocol's purpose from its encapsulation: BGP exchanges routing information but runs over TCP. Avoid treating an informal "Layer 6.5" label as a standard. The TLS 1.3 overhead example needs explicit cipher/padding assumptions; with a 16-byte AEAD tag and no padding, the record overhead is 5 + 1 + 16 = 22 bytes, not an unexplained 37. Keep Ethernet FCS and capture offloads separate from bytes actually present in the pcap.

### Module 05: IP - The Internet Protocol

**Keep:** The ordinary IPv4 subnet calculations, bit-boundary illustrations, fragmentation arithmetic, and list of special-address use cases are substantial enough.

- **Cloud-routing accuracy:** [Lab Part 6](modules/module-05-ip-the-internet-protocol.md) and the [production scenario](modules/module-05-ip-the-internet-protocol.md) teach that VPC subnets remain isolated until routes explicitly join them. AWS VPC route tables already contain a local route for the VPC CIDR; subnet boundaries alone are not access controls. The veth exercise adds on-link routes and does not demonstrate a forwarding router. Separate that lesson from routed subnet connectivity. Make the database example consistently either same-VPC or a non-overlapping peered VPC; it currently mixes a local database-subnet route with a missing peering route. Do not use failed RDS ping as the deciding evidence.
- **Lab liveness:** In [Lab Part 3](modules/module-05-ip-the-internet-protocol.md), `tcpdump -c 20` is followed by five pings and a `wait`. Normally that generates only ten matching packets, so the exercise can hang indefinitely. Use explicit bounded capture shutdown. The traceroute capture filters only ICMP but promises to display the outgoing UDP probes; include both. Do not promise a metadata route lookup fails off-cloud: an ordinary default route may still match it.
- **Accuracy:** "Everything else is public" in the [address classification](modules/module-05-ip-the-internet-protocol.md) is unsafe; use the IANA special-purpose registries and distinguish globally reachable from merely non-RFC1918. Private prefixes do not uniquely identify Docker or a cloud provider. ARP does not use the IPv4 address 255.255.255.255 because ARP is not carried in IP. Metadata access also needs provider-specific authentication and IMDSv2 considerations, not only a route check.
- **Coverage:** Add the /31 point-to-point and /32 exceptions to the usable-host formula, and distinguish VPC address-pool size from per-subnet provider reservations. The [IPv6 material](modules/module-05-ip-the-internet-protocol.md) needs an actual local RA/SLAAC/NDP lab: observe RS/RA/NS/NA, DAD, a link-local scope identifier, the RA default router, and ICMPv6 Packet Too Big. Explain RA RDNSS versus DHCPv6, that DHCPv6 does not supply the default gateway, that DAD targets solicited-node multicast, and that `[::]` also accepting IPv4 depends on `IPV6_V6ONLY`/platform behavior. The existing address-listing exercise is not enough for the stated dual-stack operational objective.

### Module 06: ARP - Address Resolution Protocol

**Keep:** The ARP packet format and the distinction between final IP destination and local next-hop MAC are particularly useful.

- **Lab blockers:** [Duplicate address detection](modules/module-06-arp-address-resolution-protocol.md) assumes an interface will receive and answer its own outbound ARP probe. That is not a reliable DAD experiment; probe an address owned by a separate controlled namespace/host and compare with an unused lab address. In the [Docker exercise](modules/module-06-arp-address-resolution-protocol.md), flushing neighbors requires `CAP_NET_ADMIN`, which the supplied container does not request. Specify the `iputils-arping` implementation for the documented flags and avoid fixed LAN addresses outside an isolated topology.
- **Accuracy:** Reconcile the [initial STALE-cache explanation](modules/module-06-arp-address-resolution-protocol.md) with the later DELAY/PROBE table: STALE can be used immediately, followed by reachability confirmation and possible probing. It does not automatically trigger a fresh broadcast first. `gc_stale_time` is not a simple per-entry expiration TTL. Separate RFC 5227 address probes from announcements, and qualify unsolicited-cache-update behavior by OS policy and whether an entry already exists.
- **Scenario accuracy:** In the [failover scenario](modules/module-06-arp-address-resolution-protocol.md), off-subnet clients resolve their local router, not the remote VIP. The adjacent router's neighbor entry for the VIP is the relevant cache; clients in other VLANs do not retain that VIP's old Ethernet MAC. Do not recommend an ARP cache timeout shorter than failover detection as a general remedy. Observe announcements, neighbor state, and bridge forwarding state at the correct hop.
- **Security precision:** Replace blanket claims that ARP spoofing is impossible in cloud networks with provider- and network-mode-specific guarantees. Docker/overlay segments hosted in a cloud still need their own analysis. Correct TLS protects authenticated application content from ARP redirection; it does not prevent redirection, traffic analysis, or denial of service.

### Module 07: ICMP, Ping, and Traceroute

**Keep:** The type/code explanation, quoted offending packet, three traceroute modes, and examples of intermediate-hop control-plane rate limiting are useful.

- **Diagnostic accuracy:** Reconcile [path interpretation](modules/module-07-icmp-ping-and-traceroute.md) with the module's own asymmetric-path caveat. Asterisks through the end, even in several probe modes, do not prove application traffic is dropped at the last responding hop. Persistent downstream loss is a clue, not proof of the precise faulty interface. Hop RTT differences are not measurements of individual forward-link delay. Low loss on a few pings also does not establish a loss-free service path.
- **Lab/scenario accuracy:** A host resolving an absent on-link neighbor does not normally send that traffic through its gateway, so [Lab Part 1](modules/module-07-icmp-ping-and-traceroute.md) cannot assume the gateway generates Host Unreachable. Use the existing routed namespace pattern to control that result. A few coarse packet sizes do not find an exact PMTU. Do not infer ICMP filtering solely from not seeing an error; confirm where the oversized packet is dropped and where the error is generated. - **Lab/code blocker:** The [epoll server](modules/module-20-sockets-and-application-level-networking.md) calls `sendall()` on a nonblocking connection with no pending-output buffer or EPOLLOUT handling. A slow reader can make it raise and terminate the server; nonblocking accept/read and HUP/ERR handling also need explicit treatment. A local socket-pair probe during this review reproduced `BlockingIOError` when the peer did not drain the send buffer; the Linux epoll lab itself was not executed. Add bounded buffered writes, handle partial progress/disconnects, and close all accepted sockets. The shell's bare `wait` includes the indefinitely running server, so wait only for the client PIDs before stopping the server.
- **Essential explanation:** TCP is a byte stream, but the [echo clients](modules/module-20-sockets-and-application-level-networking.md) assume one recv returns the complete echo of one send. Add an exercise with split/coalesced messages and explicit framing or read-until-length behavior. Explain `send` partial writes, `recv` EOF, half-close/shutdown, nonblocking connect/EINPROGRESS plus SO_ERROR, deadlines, and cancellation. Include a slow-reader test that links application backpressure to the socket queues and advertised window.
- **State/tuning accuracy:** [TIME_WAIT](modules/module-20-sockets-and-application-level-networking.md) is not controlled by `tcp_fin_timeout`; that setting concerns orphaned FIN_WAIT_2 handling. Not every close puts the local side into TIME_WAIT. The exhaustion lab has both endpoints close immediately and relies on kernel-specific loopback reuse behavior, so failure at exactly 101 attempts is not deterministic. Use an isolated namespace, controlled ownership of active close or held connections, and restore the saved settings rather than guessed defaults. Distinguish EADDRNOTAVAIL, ECONNREFUSED, backlog overflow, and descriptor exhaustion instead of attributing them to one cause.
- **Production practice:** Separate SYN backlog from the accept queue, and prove overflow with queue limits/counter deltas rather than any nonzero listening Recv-Q. A blocked thread is not automatically consuming 100% CPU, and thread stack reservation is not equivalent to resident memory. Replace universal pool/fd-size prescriptions with measured budgets. In the [database pool example](modules/module-20-sockets-and-application-level-networking.md), include transaction/cursor cleanup and account for replicas: 50 pools with maxconn 20 can demand 1000 connections from a database described as limited to 500. Mark incomplete placeholder code as illustrative, not executable.

### Module 21: Packet Capture and Analysis

**Keep:** The BPF-versus-display-filter distinction, field extraction examples, conversations view, and size-limited capture concept are useful.

- **Critical interpretation gap:** The [opening claim](modules/module-21-packet-capture-and-analysis.md) that captures contain every event with no ambiguity is false. Teach capture drops, wrong interfaces/filters, snaplen truncation, clock differences, SPAN limitations, checksum offload, TSO/GSO/GRO, duplicates from multi-interface capture, and encrypted or missing handshakes. Wireshark retransmission/RTT labels are analysis, not independent proof of on-wire loss or root cause. An outgoing host capture does not prove a frame reached the wire or peer, and an RST's source address does not prove which device generated it.
- **Lab/capture correctness:** [Full transaction Lab Part 1](modules/module-21-packet-capture-and-analysis.md) filters the web host, so it cannot promise to include DNS traffic to a different resolver. Plaintext TLS SNI is not encoded as the literal field label `server_name`; use the already-present tshark dissector. The fixed-offset ClientHello filter is a limited heuristic, not robust TCP/TLS reassembly. Use reserved nonexistent names or a controlled zone instead of assuming a random public domain will remain absent. Correlate DNS questions/replies by endpoints, transaction, question, and time rather than subtracting total counts.
- **TLS coverage:** [Decryption examples](modules/module-21-packet-capture-and-analysis.md) assume every OpenSSL-using application honors SSLKEYLOGFILE and expect TLS 1.2 CLIENT_RANDOM lines for modern TLS 1.3 traffic. Support is application/backend-specific, and TLS 1.3 uses traffic-secret labels. Match the HTTP dissector to the negotiated protocol: `http` filters/fields do not show HTTP/2. The promised certificate-failure analysis lab is absent; add a controlled TLS failure and explain which alerts/certificates are visible with and without keys.
- **Production safety:** [Capture rotation](modules/module-21-packet-capture-and-analysis.md) needs a created, writable restricted directory. With `-G`, `-W` makes tcpdump exit after the file count, unlike the wrapping `-C` ring. A 96-byte snapshot neither guarantees complete headers nor guarantees no application data. Remote capture needs noninteractive capture privileges and buffering/lifecycle control. Update Kubernetes runtime access for containerd/CRI-O rather than assuming Docker; identify the debug container and output location when retrieving its pcap.
- **Scenario accuracy:** In the [three-second-delay scenario](modules/module-21-packet-capture-and-analysis.md), the illustrated exponential schedule needs another SYN at approximately three seconds to explain success on that attempt; one retransmission after one second does not itself impose another two-second wait after an immediate reply. Timer schedules are kernel/configuration-dependent, and exact delays are clues rather than unique causes. Compare conntrack count to the configured maximum and correlate counter changes with failing traffic before prescribing limits/timeouts.

### Module 22: Observability and Troubleshooting Methodology

**Keep:** Defining the symptom precisely, establishing a baseline, changing one variable, and verifying under original conditions are the right teaching priorities. The local slow-endpoint demonstration is a useful controlled comparison.

- **Command errors:** The [DNS playbook](modules/module-22-observability-and-troubleshooting.md) uses nonexistent `dig +nocache`; the local check returned `Invalid option: +nocache`. Query an identified authoritative server or manage a controlled resolver cache instead. Select/iterate authoritative nameservers safely rather than expanding several names into one `dig @$AUTH_NS` call, and enable search processing when testing dig search behavior. In [Lab Part 3](modules/module-22-observability-and-troubleshooting.md), a refusal RST comes _from_ port 9999 to the client ephemeral port, so `tcp.dstport == 9999` excludes the intended response. The loopback-only listener example never performs the advertised off-loopback failure test.
- **Docker evidence:** [Lab Part 1](modules/module-22-observability-and-troubleshooting.md) expects a custom network's resolver file to contain the `--dns` upstream directly. Docker normally retains 127.0.0.11 there and forwards external lookups to the specified upstream. Inspect both container resolver configuration and Docker's configured upstream; do not diagnose the wrong address from output the setup does not produce.
- **Diagnostic precision:** Revise the playbooks' deterministic symptom-to-cause rules. EHOSTUNREACH/"No route to host" can result from failed neighbor resolution or an ICMP rejection even when a route exists. Refusal does not imply some application is listening on another port. An iperf3 success does not rule out size-, protocol-, endpoint-, or load-dependent network problems in the original application path. A successful test from a middle host changes source identity and potentially routing/ACLs, so binary-search reasoning needs those assumptions stated.
- **Cloud evidence:** In the [NAT incident](modules/module-22-observability-and-troubleshooting.md), a flow-log REJECT is not proof of SNAT port exhaustion, and packets routed through a NAT gateway retain the remote service as their destination, not simply the NAT gateway IP. AWS's 55,000 figure is per NAT IPv4 address and unique destination IP/port/protocol, not a universal total ActiveConnectionCount ceiling. Correlate destination-specific demand, ErrorPortAllocation, timing, and affected paths. Explain flow-log exclusions/aggregation/delivery limits and that ACCEPT does not prove end-to-end application success. The same-VPC Reachability Analyzer illustration should use the matching local route rather than a NAT default route.
- **Tracing and practical gaps:** The [traceparent example](modules/module-22-observability-and-troubleshooting.md) is not valid W3C Trace Context: use valid hexadecimal trace and parent IDs of the required lengths. Subtracting a child span from its parent does not automatically yield CPU processing time or isolate network time, especially with concurrency or missing instrumentation. Add an instrumented two-service trace exercise and a supplied sanitized flow-log dataset with questions and expected analysis; both are promised but absent from the labs. Update Azure coverage to virtual network flow logs: new NSG flow-log creation is no longer supported and that feature retires on September 30, 2027.

### Module 23: Additional Critical Topics

**Keep:** The initial DORA diagram, L4/L7 distinction, reasons time synchronization matters, and PROXY-protocol agreement warning are useful.

- **Lab blocker:** [DHCP Lab Part 1](modules/module-23-additional-critical-topics.md) says starting an ordinary Docker bridge container generates DHCP/DORA and promises "Docker's internal DHCP." Docker IPAM assigns the address without that DHCP exchange; ARP is also excluded by the UDP 67/68 capture filter. Provide a real DHCP client/server on an isolated virtual link. Do not require releasing the learner's management-interface lease. In the lease explanation, renewal uses DHCPREQUEST and retries; IPv6 link-local addresses exist independently of DHCP failure, and IPv4 fallback depends on client configuration.
- **Proxy lab verification:** In [Lab Part 2](modules/module-23-additional-critical-topics.md), X-Forwarded-For is added to the upstream request and is not automatically visible in client-side curl response headers. Observe it in a backend echo/log or backend-side capture. The `/health` endpoint only proves nginx can return a static response; it is not an active backend health check. Distinguish nginx open-source passive failure handling from an active-health-check feature, and avoid requiring strict alternation across multiple workers. Include a forged-header test and a trusted-proxy boundary rather than trusting the leftmost XFF value unconditionally.
- **Scenario contradiction:** The [ALB example](modules/module-23-additional-critical-topics.md) starts with backend keepalive 65 seconds and ALB idle timeout 60 seconds, already satisfying its proposed fix. An idle timer is not a fixed connection lifetime that necessarily fires at 60 seconds after a request at 59 seconds. Rebuild the scenario around an evidenced target-side early close, showing the two connection legs, packet timing, and relevant ALB log fields. Neither a TIME_WAIT count nor `target_processing_time=0` uniquely establishes this cause, and the "most common" ranking is unsourced.
- **Missing outline objectives:** Add NTP security, including authenticated time/NTS and restricted service exposure, and a practical explanation of HTTP CONNECT. The outline includes these, but the module omits the NTP-security section and does not explain CONNECT. Correct the uppercase `HTTP_PROXY` example for an HTTPS curl request; use the documented HTTPS proxy setting or explicit proxy option and cover NO_PROXY. Stratum is distance from a reference clock, not a guarantee of clock accuracy; explain offset/delay uncertainty and the risks of stepping clocks.
- **Reference error:** The [NTP reference](modules/module-23-additional-critical-topics.md) labels RFC 7950 "NTP Version 4." [RFC 7950](https://datatracker.ietf.org/doc/rfc7950/) actually specifies the YANG 1.1 data modeling language. Use RFC 5905 for NTPv4 and RFC 8915 for NTS. Keep the protocol references and the operational chrony/provider documentation distinct.

### Module 26 (numbered 24 when reviewed): Capstone Labs

**Keep:** The six chosen incident categories are relevant. The independent-diagnosis objective should remain, but the exercises currently reveal the answers and several do not instantiate their stated failure.

- **Capstone 6: safety and liveness blocker.** The [NAT simulation](modules/module-26-capstone-labs.md) lowers the host's conntrack maximum, starts a long-lived HTTP server, launches clients without timeouts, and uses bare `wait` before restoration. That wait also includes the server, so normal execution does not reach the restore/kill steps. Use a disposable isolated environment, explicit client PIDs, bounded requests, and guaranteed rollback. There is no routed NAT gateway in the supplied topology, no flow-log/trace fixture, and no packet-capture command supporting the printed retransmission "evidence." Conntrack-table exhaustion and SNAT-port exhaustion are different mechanisms. A 15% failure rate must be measured or clearly identified as scenario text, not promised output.
- **Capstone 2: faults do not match Docker behavior.** The [DNS challenges](modules/module-26-capstone-labs.md) put both clients on a user-defined network, where `--dns` configures forwarding for external queries while Docker's embedded resolver can still answer `backend`. Thus the two promised internal-name failures need not occur, and the stated resolver-file output is wrong. Recreating the backend may reuse its old IP, and calling nslookup does not demonstrate a persistent client cache. Supply real wrong-upstream, missing-alias/search, private-zone, and TTL/cache variants with controlled expected failures.
- **Capstone 3: wrong receiver and unsupported diagnosis.** The [download lab](modules/module-26-capstone-labs.md) shrinks the server's receive buffer, but the client receives the large file. Delay/loss is configured only on client egress, the claimed 100 Mbps link is not shaped, and no PMTUD fault is created. Apply each constraint to the correct direction and endpoint, establish the actual RTT/rate/window, and control offloads. `io,stat` is traffic-volume statistics, not RTT analysis. Comparing counts of zero-window events and retransmissions cannot identify a bottleneck by majority vote; require one-factor experiments and measured before/after goodput. Track and stop the background server before deleting its namespace.
- **Capstone 4: validate the proposed repair.** The [certificate lab](modules/module-26-capstone-labs.md) has the right root/intermediate/leaf topology. Explicitly configure the intermediate chain for the tested OpenSSL `s_server` using its documented `-cert_chain` option rather than assuming concatenation passed to `-cert` is sufficient. Inspect the actually served chain, require hostname and chain verification, check curl's exit status, and wait for the old listener to stop before restarting. Specify CA constraints/key usage and restrict private-key files. A printed "VERIFIED" after a grep is not an assertion.
- **Capstone 1: protocol-consistent evidence.** In the [full trace](modules/module-26-capstone-labs.md), `%{ssl_verify_result}` is a certificate verification result, not the TLS version. HTTP/2 must be analyzed with HTTP/2 fields, TLS 1.3 encrypted handshake messages need the key log, and fixed packet numbers are not portable protocol boundaries. Match the capture to the resolved endpoint, preserve intended DNS traffic, account for connection reuse, and grade correct interpretation rather than a prescribed packet count.
- **Capstone 5: make diagnosis genuinely independent.** The [Kubernetes maze](modules/module-26-capstone-labs.md) only injects a clearly named ingress-deny policy. Require a policy-capable CNI and test an allowed client and a still-denied client after remediation. Add separate selector/targetPort, DNS, and cross-node connectivity variants without placing the answer beside the command. Use EndpointSlices and bounded readiness checks. Do not classify every DNS failure as CoreDNS itself failing.
- **Assessment:** Separate setup, learner brief, optional hints, and instructor solution. A passing submission should identify the failing flow and observation point, reject at least one plausible alternative, justify a minimal fix, retest the original workload, and demonstrate cleanup. These exercises currently function more as guided demonstrations than evidence of mastery.
