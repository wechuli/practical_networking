# Module 6: ARP — Address Resolution Protocol

> **Audience:** Support Engineers · Developers · Cloud Engineers
> **Prerequisites:** Module 5 — IP — The Internet Protocol
> **Estimated time:** 2–3 hours (the lab runs offline in network namespaces)

## Overview

You know the destination IP address. Your routing table says the next hop is on the local network. You need to put the packet into an Ethernet frame and send it out the wire. But Ethernet frames are addressed by MAC address, not IP address. How do you get the destination's MAC address when all you have is an IP?

ARP — Address Resolution Protocol — answers that question. It is the protocol that bridges Layer 3 (IP) and Layer 2 (Ethernet). Without ARP, a host that knows a destination IP has no way to deliver a frame on the local network. ARP is invisible when it works. When it does not, the host appears completely unreachable even though its IP is correct, its interface is up, and its routing table is right. The errors are distinctive once you know them: after about three seconds of unanswered ARP requests, ping prints `From <your own IP> … Destination Host Unreachable` and a TCP connect fails with `No route to host` (EHOSTUNREACH) — both generated by your own kernel, not by any router. A *stale* mapping is worse: packets go to the wrong MAC and simply vanish, with no error at all.

ARP problems are among the most confusing to diagnose because they produce Layer 3 symptoms (packets not arriving) from a Layer 2 cause (cannot resolve the MAC address). This module teaches you how ARP works, what the ARP cache looks like in normal and failed states, what gratuitous ARP does and why it matters for failover, how ARP spoofing works as an attack, and how cloud environments modify or replace ARP entirely.

## What You Will Build Toward

- Explain why Layer 2 delivery requires a MAC address even when you have the IP address
- Describe the ARP request/reply sequence and identify both in a packet capture
- Read the ARP cache on a Linux machine and recognize REACHABLE, STALE, and FAILED states
- Explain gratuitous ARP and why it is critical for virtual IP failover
- Understand ARP spoofing: how it works, why it is dangerous, and how to detect it
- Explain how cloud environments (AWS, GCP, Azure) handle ARP differently from physical networks, and why VIP failover there needs an API call
- Measure how long a failover takes without gratuitous ARP, and see proxy ARP make a Kubernetes pod's gateway work

## 6.1 The Problem ARP Solves

### What This Is

When your host wants to send a packet to another host on the same local network, it must construct an Ethernet frame. An Ethernet frame's header requires a 6-byte destination MAC address. The sending host knows the destination IP address — it got that from DNS, from a configuration file, from the routing table's next-hop entry. But the Ethernet hardware does not understand IP addresses. It only understands MAC addresses.

This is the fundamental boundary between Layer 3 and Layer 2:

- **Layer 3 (Network):** Addresses are IP addresses. Routers forward packets based on IP.
- **Layer 2 (Data Link):** Addresses are MAC addresses. Switches forward frames based on MAC.

The sending host needs a translation mechanism: given an IP address on the local network, find the corresponding MAC address. That mechanism is ARP.

### When ARP Is Used

ARP is used only for local delivery — when the destination IP is on the same subnet (same broadcast domain) as the sender. If the destination is on a different subnet, the packet goes to the default gateway, and the ARP lookup is for the gateway's MAC address, not the final destination's.

```
WHEN IS ARP NEEDED?

  Case 1: Destination is on the same subnet
  ─────────────────────────────────────────
  Host A (10.0.1.10) wants to send to Host B (10.0.1.20)
  Both are on 10.0.1.0/24 — same subnet

  Host A needs Host B's MAC → ARP for 10.0.1.20

  [Host A] ──ARP: Who has 10.0.1.20?──▶ [Switch] ──▶ [Host B]
  [Host A] ◀──ARP: 10.0.1.20 is at aa:bb:cc:dd:ee:ff── [Host B]
  [Host A] ──Ethernet frame dst=aa:bb:cc:dd:ee:ff──▶ [Host B]


  Case 2: Destination is on a different subnet
  ─────────────────────────────────────────────
  Host A (10.0.1.10) wants to send to Server (10.0.5.20)
  Different subnets — routing table says next hop is gateway 10.0.1.1

  Host A needs the GATEWAY's MAC → ARP for 10.0.1.1 (not 10.0.5.20)

  [Host A] ──ARP: Who has 10.0.1.1?──▶ [Gateway/Router]
  [Host A] ◀──ARP: 10.0.1.1 is at 11:22:33:44:55:66── [Gateway]
  [Host A] ──Frame dst=11:22:33:44:55:66, IP dst=10.0.5.20──▶ [Gateway]
                                                                    │
           Note: the Ethernet destination is the gateway's MAC,     │
           but the IP destination is the final server. The gateway   │
           strips the Ethernet header, looks at the IP destination, │
           and re-encapsulates in a new frame for the next hop.     │
                                                                    ▼
                                                          [Server 10.0.5.20]
```

### Key Insight

**The Ethernet source and destination MACs change at every hop. The IP destination stays the same for the entire journey.** This is encapsulation in action: the Layer 2 header is rewritten at each router, but the Layer 3 header remains unchanged (except TTL decrement and header checksum recalculation — and NAT, Module 9, which deliberately rewrites addresses). A capture on the client side of a router therefore shows the *router's* MAC as the destination for every remote server; that is normal, not a misconfiguration.

## 6.2 How ARP Works

### What This Is

ARP (RFC 826, 1982) is a simple request-reply protocol that maps IPv4 addresses to MAC addresses. It operates directly on Layer 2 — ARP packets are Ethernet frames with EtherType 0x0806. They are not IP packets. ARP has no IP header, no TCP/UDP header, no port numbers. It sits beside IP, not inside it — which is why an `iptables` rule never sees ARP (`arptables`/`nft` `arp` family and bridge filtering do) and why `tcpdump 'ip'` misses it; use `tcpdump arp`.

IPv6 does not use ARP. Neighbor Discovery (Module 5.5) does the same job with ICMPv6, and Linux keeps both in one neighbor table: `ip neigh` shows IPv4 and IPv6 entries with the same states.

### The ARP Process — Step by Step

```
ARP REQUEST-REPLY SEQUENCE

  Step 1: Host A checks its ARP cache
  ──────────────────────────────────
  Does Host A already know the MAC for 10.0.1.20?
  → Check: ip neigh show | grep 10.0.1.20
  → If found and REACHABLE: use the cached MAC. Done. No ARP needed.
  → If STALE: send with the cached MAC immediately, and confirm it a few
    seconds later (DELAY, then PROBE — see the state table below).
  → If absent: queue the packet and proceed to Step 2.


  Step 2: Host A sends an ARP Request (broadcast)
  ────────────────────────────────────────────────
  Source MAC:  Host A's MAC (aa:aa:aa:aa:aa:aa)
  Dest MAC:    ff:ff:ff:ff:ff:ff (Ethernet broadcast — every host on segment)
  EtherType:   0x0806 (ARP)
  Operation:   1 (ARP Request)
  Sender IP:   10.0.1.10
  Sender MAC:  aa:aa:aa:aa:aa:aa
  Target IP:   10.0.1.20
  Target MAC:  00:00:00:00:00:00 (unknown — this is what we're asking)

  "Who has 10.0.1.20? Tell 10.0.1.10"

  This broadcast reaches EVERY host on the local segment.
  Every host receives it. Only 10.0.1.20 responds.


  Step 3: Host B sends an ARP Reply (unicast)
  ────────────────────────────────────────────
  Source MAC:  Host B's MAC (bb:bb:bb:bb:bb:bb)
  Dest MAC:    aa:aa:aa:aa:aa:aa (directed back to Host A)
  EtherType:   0x0806 (ARP)
  Operation:   2 (ARP Reply)
  Sender IP:   10.0.1.20
  Sender MAC:  bb:bb:bb:bb:bb:bb
  Target IP:   10.0.1.10
  Target MAC:  aa:aa:aa:aa:aa:aa

  "10.0.1.20 is at bb:bb:bb:bb:bb:bb"

  This is unicast — sent directly to Host A, not broadcast.

  Host B also caches Host A's mapping from the request itself, so the
  conversation needs no second ARP exchange in the other direction.


  Step 4: Host A caches the result
  ─────────────────────────────────
  Host A stores: 10.0.1.20 → bb:bb:bb:bb:bb:bb (REACHABLE)
  Now Host A can construct the Ethernet frame and send the IP packet.

  Reachability has an aging timer, not a simple DNS-style cache TTL.
  STALE can transmit immediately; DELAY then PROBE can confirm reachability.
  TCP traffic confirms reachability as a side effect (an ACK proves the
  neighbor is alive), so busy TCP peers rarely need probes; ICMP and UDP
  do not, so their entries are probed every so often.
```

### The ARP Packet Format

```
ARP PACKET STRUCTURE (28 bytes for IPv4 over Ethernet)

  ┌────────────────────────────────────────────────────────────┐
  │ Hardware Type (2 bytes)     = 0x0001 (Ethernet)            │
  │ Protocol Type (2 bytes)     = 0x0800 (IPv4)                │
  │ Hardware Addr Len (1 byte)  = 6 (MAC = 6 bytes)            │
  │ Protocol Addr Len (1 byte)  = 4 (IPv4 = 4 bytes)           │
  │ Operation (2 bytes)         = 1 (Request) or 2 (Reply)     │
  ├────────────────────────────────────────────────────────────┤
  │ Sender Hardware Address (6 bytes)  = Sender's MAC          │
  │ Sender Protocol Address (4 bytes)  = Sender's IP           │
  │ Target Hardware Address (6 bytes)  = Target's MAC           │
  │                                      (00:00:00:00:00:00    │
  │                                       in requests)         │
  │ Target Protocol Address (4 bytes)  = Target's IP            │
  └────────────────────────────────────────────────────────────┘

  Total: 28 bytes of ARP payload inside an Ethernet frame — 42 bytes with
  the 14-byte Ethernet header, padded to the 60-byte minimum on a real wire
  (tcpdump on the sender shows "length 42", before padding).

  In an ARP Request:
    Target Hardware Address = all zeros (unknown)
    Ethernet destination = ff:ff:ff:ff:ff:ff (broadcast)

  In an ARP Reply:
    Target Hardware Address = requester's MAC (now known)
    Ethernet destination = requester's MAC (unicast)
```

### The ARP Cache

Every host maintains an ARP cache (also called the ARP table or neighbor table) — a mapping of IP addresses to MAC addresses for recently resolved neighbors.

**Viewing the cache:**

```bash
# Modern Linux (recommended)
ip neigh show

# Legacy command (still works)
arp -n
```

**ARP cache states in Linux (managed by the kernel's neighbor subsystem):**

```

───────────   ────────────────────────────────────     ──────────────────────

              responded to an ARP request or sent      directly. No ARP needed.
              traffic recently.

                                                        moves to DELAY.
```

**The timers that produce those states** (Linux defaults, per interface under `net.ipv4.neigh.<if>.`):

| Setting | Default | Effect |
| --- | --- | --- |
| `base_reachable_time_ms` | 30000 | REACHABLE lasts a random 0.5–1.5 × this: 15–45 s |
| `delay_first_probe_time` | 5 | seconds in DELAY before probing |
| `ucast_solicit` | 3 | unicast probes to the cached MAC (PROBE), 1 s apart |
| `mcast_solicit` | 3 | broadcast requests for a new entry, 1 s apart |
| `retrans_time_ms` | 1000 | spacing of those requests |
| `locktime` | 1 s | an entry updated less than this long ago ignores conflicting replies (first answer wins) |
| `gc_stale_time` | 60 | unused entries become eligible for garbage collection |

Two numbers fall out of the table and are worth remembering. **Resolving a missing host fails after 3 s** (3 broadcasts × 1 s) — the lab measures it. **A mapping that silently became wrong** (the IP moved to another MAC, nobody announced it) is corrected only after the entry ages out of REACHABLE, waits in DELAY, and fails three unicast probes: up to about 45 + 5 + 3 ≈ 53 s with defaults. The lab measures 12–21 s with a shortened reachable time.

## 6.3 Gratuitous ARP

### What This Is

A gratuitous ARP is an ARP announcement where a host broadcasts its own IP-to-MAC mapping without being asked. It is an ARP request or reply where the sender IP and the target IP are the same — the host is answering a question nobody asked: "10.0.1.100 is at aa:bb:cc:dd:ee:ff."

**Linux does not send one by itself** when you add an address or bring an interface up (`net.ipv4.conf.<if>.arp_notify` defaults to 0; with 1 the kernel announces when the interface's MAC changes or a driver signals a VM migration — in the lab, taking a veth down and up did not trigger one). Failover software sends its own — keepalived, Pacemaker's IPaddr2, `arping -U`. The lab shows the silence and its cost.

### Why Gratuitous ARP Exists

Gratuitous ARP serves three purposes:

**1. Announce an address mapping.** A host can send an unsolicited announcement.
Whether receivers create or update entries depends on existing state and OS policy.
Linux **updates an entry it already has** (the lab shows this) but, with the default
`arp_accept=0`, **does not create a new entry** from an announcement — a host that
has never talked to the VIP learns it the normal way, by asking. Broadcasts can be
lost, so senders repeat them.

**2. Detect conflicts.** RFC 5227 probes use sender IP 0.0.0.0 before assigning a
candidate address. Announcements use the claimed address as both sender and target.
They serve related but different purposes; silence is not proof of permanent uniqueness.

**3. Failover — Virtual IP (VIP) takeover.** This is the most important production use case. When a primary server fails and a standby takes over the virtual IP, the standby sends a gratuitous ARP to tell all neighbors: "This IP is now at my MAC address." Without this, neighbors would continue sending frames to the old (dead) server's MAC until their ARP cache entries expire — which could take minutes.

### Gratuitous ARP on the Wire

```
GRATUITOUS ARP REQUEST (most common form):
  Ethernet dst:     ff:ff:ff:ff:ff:ff  (broadcast)
  Ethernet src:     bb:bb:bb:bb:bb:bb  (standby's MAC)
  ARP Operation:    1 (Request)
  Sender IP:        10.0.1.200         (the VIP)
  Sender MAC:       bb:bb:bb:bb:bb:bb  (standby's MAC)
  Target IP:        10.0.1.200         ← SAME as sender IP (this makes it gratuitous)
  Target MAC:       00:00:00:00:00:00 (iputils `arping -U` puts ff:ff:ff:ff:ff:ff
                                       here; tcpdump then prints it in parentheses)

  tcpdump -e (from the lab):
  02:00:00:00:06:0a > ff:ff:ff:ff:ff:ff, ethertype ARP (0x0806), length 42:
      Request who-has 198.18.6.100 (ff:ff:ff:ff:ff:ff) tell 198.18.6.100, length 28

  Key identifier: Sender IP == Target IP → this is gratuitous.

GRATUITOUS ARP REPLY (alternative form, used by some implementations):
  ARP Operation:    2 (Reply)
  Sender IP:        10.0.1.200
  Sender MAC:       bb:bb:bb:bb:bb:bb
  Target IP:        10.0.1.200
  Target MAC:       ff:ff:ff:ff:ff:ff   (or bb:bb:bb:bb:bb:bb)
```

### Where You See Gratuitous ARP in Production

- **keepalived / VRRP:** When a VRRP master fails and the backup takes over, it sends gratuitous ARPs for every virtual IP.
- **HAProxy / load balancer failover:** Active/passive LB pairs use gratuitous ARP during VIP transition.
- **Kubernetes bare-metal load balancers:** MetalLB in Layer 2 mode answers ARP for a Service's external IP from one node and sends gratuitous ARPs when that IP moves to another node. Slow failover there is this module's problem.
- **Interface startup:** Windows and macOS announce or probe addresses as they configure them; Linux leaves it to userspace (DHCP clients, NetworkManager's duplicate-address check) or to `arp_notify=1` for MAC changes.
- **Not in the cloud:** reassigning an AWS Elastic IP changes a 1:1 NAT mapping at the provider's edge, and moving a secondary private IP between instances is an API call. Neither involves ARP inside your VM, and a gratuitous ARP from your VM cannot move an address (6.5).

## 6.4 ARP Spoofing

### What This Is

ARP spoofing (also called ARP poisoning) is an attack where a malicious host sends forged ARP replies or announcements to associate its own MAC address with another host's IP address. Hosts that already have an entry for that IP update it with the forged mapping, and traffic intended for the legitimate host is redirected to the attacker. The same mechanics happen *accidentally* whenever two machines are configured with one IP address — an IP conflict looks exactly like a slow, unintentional spoofing attack, and is far more common.

ARP has no authentication. There is no way for a host to verify that an ARP reply is legitimate. Any host on the segment can claim to be any IP address. This is a fundamental design weakness of ARP — it was designed for trusted environments (academic networks in the 1980s), not adversarial ones.

### How ARP Spoofing Works

```
ARP SPOOFING — MAN-IN-THE-MIDDLE ATTACK

  Normal state:
  [Client 10.0.1.10] ──traffic for gateway──▶ [Gateway 10.0.1.1]
  Client ARP cache: 10.0.1.1 → GW_MAC


  Attacker sends forged ARP reply to client:
  "10.0.1.1 is at ATTACKER_MAC"   ← LIE

  [Attacker 10.0.1.99]
     │
     │  Forged ARP Reply (unsolicited):
     │  Sender IP:  10.0.1.1        ← Claims to be the gateway
     │  Sender MAC: ATTACKER_MAC    ← But gives its own MAC
     │
     ▼
  [Client 10.0.1.10]
  ARP cache: 10.0.1.1 → ATTACKER_MAC   ← POISONED


  Now all traffic from client to gateway goes to attacker:
  [Client] ──traffic for 10.0.1.1──▶ [Attacker] ──forwards──▶ [Gateway]
                                          │
                                          └── Attacker can:
                                              • Read all unencrypted traffic
                                              • Modify packets in transit
                                              • Drop packets selectively
                                              • Capture credentials (HTTP, FTP, etc.)


  Attacker also poisons the gateway:
  "10.0.1.10 is at ATTACKER_MAC"

  Now the attacker sits in the middle of BOTH directions:
  [Client] ◀──▶ [Attacker] ◀──▶ [Gateway]
       Full man-in-the-middle position
```

### Why ARP Spoofing Works

- ARP has no authentication mechanism. Any host can send any ARP reply at any time.
- Hosts accept ARP replies and announcements they did not ask for, and update an existing entry with them (Linux: after `locktime`, 1 s, has passed since the last update). With `arp_accept=0` they do not create new entries from them, which is why attackers target addresses their victims already use — the gateway above all.
- The most recent answer wins. A legitimate entry is replaced by a forged one, then possibly back again: an entry "flapping" between two MACs is the signature of both spoofing and IP conflicts.
- The attack only works on the local Layer 2 segment. An attacker must be on the same broadcast domain.

### Detection and Prevention

```
DETECTION:
  arpwatch         Monitors ARP traffic. Alerts on IP/MAC changes.
                   Detects: "flip flop" = MAC for an IP keeps changing.

  tcpdump          Manual detection:
                   sudo tcpdump -i eth0 -nn arp
                   Watch for: multiple different MACs claiming the same IP.

  Wireshark        Expert Info → Duplicate IP address detected.
                   Filter: arp.duplicate-address-detected


PREVENTION:
  Dynamic ARP Inspection (DAI)
                   Switch-level feature. The switch validates ARP packets
                   against a DHCP snooping binding table. ARP replies that
                   don't match the known IP-to-MAC binding are dropped.

  Static ARP entries
                   Manually configure critical mappings (e.g., the gateway):
                   sudo ip neigh replace 10.0.1.1 lladdr aa:bb:cc:dd:ee:ff dev eth0 nud permanent
                   Permanent entries are not overwritten by ARP replies.

  802.1X           Port-based access control. Only authenticated devices
                   can send traffic, including ARP.

  Use TLS/HTTPS    Even if traffic is redirected via ARP spoofing, an
                   attacker cannot read or modify correctly authenticated
                   TLS traffic. They can still drop it (denial of service),
                   see who talks to whom, and attack anything unencrypted
                   or any client that skips certificate verification.
```

### Production Relevance

ARP spoofing is less relevant in cloud environments (where ARP is controlled by the hypervisor — see section 6.5) and more relevant in:

- **On-premises corporate networks:** where rogue devices can be plugged in
- **Shared hosting environments:** where multiple tenants share a Layer 2 segment
- **Docker bridge networks:** containers on the same bridge can ARP-spoof each other
- **Lab and development environments:** often lack the switch-level protections of production networks

## 6.5 Proxy ARP and ARP in Cloud

### Proxy ARP

Proxy ARP is when a device (typically a router) answers ARP requests on behalf of another host that is on a different network. The router responds with its own MAC address, so the sender sends the frame to the router, which then forwards the packet to the actual destination.

```
PROXY ARP

  Host A (10.0.1.10) wants to reach Host C (10.0.2.50)
  Host A was configured with 10.0.1.10/8 instead of /24, so it thinks
  10.0.2.50 is on the local network and ARPs for it directly.

  Without Proxy ARP:
  Host A sends ARP broadcast: "Who has 10.0.2.50?"
  No one on the local /24 segment has that IP. ARP fails. Packets dropped.

  With Proxy ARP (router has it enabled):
  Host A sends ARP broadcast: "Who has 10.0.2.50?"
  Router (10.0.1.1) has a route to 10.0.2.0/24 and replies:
  "10.0.2.50 is at ROUTER_MAC"
  Host A sends packets to ROUTER_MAC. Router forwards to 10.0.2.50.

  Proxy ARP masks misconfiguration. It makes things work when they
  should not. This can hide real problems. Most networks disable it
  on routers facing ordinary LANs.
```

A Linux interface with `proxy_arp=1` answers a request only if the kernel has a route to the target **through a different interface**; with no matching route (not even a default), it stays silent.

**Proxy ARP on purpose: Kubernetes pods.** Calico's pods have a single /32 address and a default route `via 169.254.1.1 dev eth0` — an address that exists nowhere. The host side of each pod's veth has `proxy_arp` set, so when the pod ARPs for 169.254.1.1, the host answers with its own interface MAC and then routes the packet. The lab builds exactly this. (The AWS VPC CNI uses the same gateway address but writes a static neighbor entry into the pod instead.) Two practical consequences:

- A pod whose first packet takes a few hundred milliseconds may be waiting on proxy ARP: Linux delays proxy replies by a random amount up to `net.ipv4.neigh.<if>.proxy_delay` (default 80, in hundredths of a second: up to 0.8 s; the lab measured 318 ms). A CNI that relies on proxy ARP should set it to 0; check what yours does with `sysctl` on the host interface.
- If the pod can't reach anything and `ip neigh` inside it shows `169.254.1.1 FAILED`, the host-side interface lost `proxy_arp` or its route to the pod — a node-side problem, not a pod one.

**Check and control Proxy ARP on Linux:**

```bash
# Check if Proxy ARP is enabled on an interface
cat /proc/sys/net/ipv4/conf/eth0/proxy_arp
# 0 = disabled (default), 1 = enabled

# Disable Proxy ARP
sudo sysctl -w net.ipv4.conf.eth0.proxy_arp=0
```

### ARP in Cloud Environments

Cloud VPCs (AWS, GCP, Azure) do not use traditional ARP on a physical shared Ethernet segment. The network is virtualized: the provider's virtual switch intercepts ARP and answers from its own records of which address belongs to which NIC. There is no real broadcast domain, and broadcast and multicast traffic are not delivered between VMs.

What a guest actually sees differs by provider:

| Provider | Guest's view | Source |
| --- | --- | --- |
| AWS | ARP is answered with the target ENI's MAC | provider behavior; check `ip neigh` on an instance |
| Azure | Every ARP request is answered with the same MAC, `12:34:56:78:9a:bc`, whatever the IP | Microsoft Q&A answer from Microsoft staff (not product documentation) |
| Google Cloud | Linux instances get a `/32` address, so they ARP only for the gateway and send all traffic to its MAC; with a subnet-sized netmask, Google Cloud intercepts ARP and answers even for addresses no instance uses | [Compute instance netmasks](https://cloud.google.com/vpc/docs/compute-instance-netmasks) |

**Consequence for failover:** a gratuitous ARP from a VM moves nothing, because the provider, not the guest, decides which NIC an IP belongs to. keepalived-style VIP failover in a VPC needs an API call on takeover (reassign a secondary private IP, move an Elastic/public IP, or update a route table entry), usually with VRRP in unicast mode because multicast is not delivered. A design that works on-premises and "fails silently" after migrating to the cloud is often this.

```
ARP IN A PHYSICAL NETWORK vs CLOUD VPC

  Physical Network:
  ┌────────┐  ARP broadcast  ┌────────┐
  │ Host A │ ──────────────▶ │ Host B │
  │        │ ◀────────────── │        │
  └────────┘  ARP reply      └────────┘
  Both hosts are on a real shared Ethernet segment.
  The switch floods the ARP broadcast to all ports in the VLAN.


  Cloud VPC (e.g., AWS):
  ┌────────┐  ARP request    ┌──────────────┐
  │  VM A  │ ──────────────▶ │  Hypervisor  │
  │        │ ◀────────────── │  (virtual     │
  └────────┘  ARP reply      │   switch)     │
                              └──────────────┘
  The hypervisor knows every VM's IP and MAC.
  It answers ARP requests instantly from its own table.
  No broadcast reaches other VMs — ARP is contained.

  This means:
  ✓ Spoofing another VM's address does not work: the provider answers
    ARP and checks source addresses (unless you disable that check,
    e.g. AWS "source/destination check" for NAT instances)
  ✓ Broadcast storms from ARP cannot happen
  ✗ Gratuitous-ARP failover does not work (see above)
  ✗ Debugging ARP in cloud is harder — tcpdump arp shows only your side
  Guest-created bridges and overlays (Docker, a CNI) are real L2
  segments again, with all of this module's behavior.
```

### Overlay Networks and ARP Suppression

In overlay networks (VXLAN, used by Docker overlay and many Kubernetes CNIs), ARP is often suppressed or proxied at the VTEP (VXLAN Tunnel Endpoint). Flannel's VXLAN backend, for example, writes static neighbor and FDB entries for each remote node instead of letting ARP flood (`ip neigh show dev flannel.1` and `bridge fdb show dev flannel.1` on a node list them); Module 16 covers CNIs. Instead of broadcasting ARP across the entire overlay, the VTEP has a distributed IP-to-MAC table and answers ARP locally. This prevents ARP broadcasts from being tunneled across the underlay network, which would negate much of the benefit of overlays.

```
ARP IN VXLAN OVERLAY NETWORKS

  Without ARP suppression:
  ARP broadcast from Container A must be encapsulated in VXLAN,
  sent to every VTEP in the overlay, decapsulated, and broadcast
  on every local segment. This is expensive and does not scale.

  With ARP suppression:
  ┌──────────┐   ARP request    ┌──────────┐
  │Container │ ────────────────▶│   VTEP   │
  │    A     │ ◀────────────────│ (knows   │
  └──────────┘   ARP reply      │  the MAC │
                 (from VTEP)    │  table)  │
                                └──────────┘
  VTEP answers from its learned table. No broadcast across the overlay.
  The ARP request never leaves the local host.
```

**Resolution, and learning from the request.**

```
check 1/33: first contact: a broadcast request, a unicast reply
  | 02:00:00:00:06:01 > ff:ff:ff:ff:ff:ff, ethertype ARP (0x0806), length 42: Request who-has 198.18.6.10 tell 198.18.6.1, length 28
```

web1's entry is already in DELAY: it learned the client from the request (STALE), used it to send the echo reply, and will confirm it in 5 s.

**Aging and probing.** After 6–18 s without confirmation the client's entry is `STALE` (check 4). The next ping uses it at once — the state flips to DELAY — and 5 s later the kernel confirms the mapping with a *unicast* request to the MAC it already has:

```
check 5/33: using a STALE entry: send at once (DELAY), then confirm with a UNICAST request 5 s later (PROBE)
  | 64 bytes from 198.18.6.10: icmp_seq=1 ttl=64 time=0.038 ms
  | 198.18.6.10 dev eth0 lladdr 02:00:00:00:06:0a DELAY
  | 198.18.6.10 dev eth0 lladdr 02:00:00:00:06:0a REACHABLE
  | 18:31:54.456230 02:00:00:00:06:01 > 02:00:00:00:06:0a, … Request who-has 198.18.6.10 tell 198.18.6.1, length 28
  | 18:31:54.458938 02:00:00:00:06:0a > 02:00:00:00:06:01, … Reply 198.18.6.10 is-at 02:00:00:00:06:0a, length 28
```

No broadcast at all (the check asserts it): STALE entries are refreshed point to point. A ping does not confirm reachability, so the probe is needed; with TCP traffic the ACKs would have confirmed it and the probe would never be sent.

**Resolution failure, timed.**

```
check 6/33: nobody owns 198.18.6.99: three broadcasts one second apart, then ping reports the failure
  | From 198.18.6.1 icmp_seq=1 Destination Host Unreachable
  | 18:31:56.204322 02:00:00:00:06:01 > ff:ff:ff:ff:ff:ff, … Request who-has 198.18.6.99 tell 198.18.6.1
  | 18:31:57.208154 02:00:00:00:06:01 > ff:ff:ff:ff:ff:ff, … Request who-has 198.18.6.99 tell 198.18.6.1
  | 18:31:58.232138 02:00:00:00:06:01 > ff:ff:ff:ff:ff:ff, … Request who-has 198.18.6.99 tell 198.18.6.1
```

`mcast_solicit` (3) × `retrans_time_ms` (1 s): the error arrives about 3 s after the first packet, **from your own address**. Any time you see an application connect fail with "No route to host" after roughly 3 s to an on-link address, this is what happened.

**VIP failover without gratuitous ARP — measured.** The VIP 198.18.6.100 moves from web1 to web2 the way a careless script would: delete on one, add on the other. Linux announces nothing (check 10 captures zero ARP packets), so the client keeps sending to web1's MAC, and web1 drops packets for an address it no longer has:

```
check 11/33: the client still sends to web1's MAC, which drops the packets
  | 1 packets transmitted, 0 received, 100% packet loss, time 0ms
  | 198.18.6.100 dev eth0 lladdr 02:00:00:00:06:0a REACHABLE
check 12/33: recovery without gratuitous ARP: the entry must age, be probed (unicast, to the old MAC), fail, and be re-resolved
  | recovered after 13120 ms
  | 18:32:12.888132 02:00:00:00:06:01 > 02:00:00:00:06:0a, … Request who-has 198.18.6.100 tell 198.18.6.1
  | 18:32:13.912138 02:00:00:00:06:01 > 02:00:00:00:06:0a, … Request who-has 198.18.6.100 tell 198.18.6.1
  | 18:32:14.936138 02:00:00:00:06:01 > 02:00:00:00:06:0a, … Request who-has 198.18.6.100 tell 198.18.6.1
```

Read the capture as the state machine: three unicast probes to the *old* MAC (PROBE), one second apart, unanswered; the entry fails; the next packet starts a fresh broadcast, and web2 answers. Across four runs the outage was 11.6, 13.1, 18.9, and 21.1 s — random because REACHABLE lasts a random 0.5–1.5 × the base time. With the default 30 s base it is up to about 53 s.

**The same failover with a gratuitous ARP.**

```
check 15/33: this time web1 announces itself with a gratuitous ARP: sender IP = target IP, broadcast
  | 02:00:00:00:06:0a > ff:ff:ff:ff:ff:ff, … Request who-has 198.18.6.100 (ff:ff:ff:ff:ff:ff) tell 198.18.6.100, length 28

```

One broadcast frame turns a 13–21 s outage into none. The entry is STALE rather than REACHABLE because an announcement proves who claims the address, not that the path works; normal traffic confirms it afterwards.

**Announcements, conflicts, and poisoning.**

```
check 19/33: Linux does not create entries from announcements (arp_accept=0): nothing cached for 198.18.6.77
check 22/33: one ARP request, two different answers
  | ARPING 198.18.6.11 from 198.18.6.1 eth0
  | Unicast reply from 198.18.6.11 [02:00:00:00:06:66]  0.559ms
  | Unicast reply from 198.18.6.11 [02:00:00:00:06:0B]  0.594ms

check 23/33: duplicate address detection (probe from 0.0.0.0) finds 198.18.6.11 taken: exit 1
check 24/33: and 198.18.6.50 apparently free: exit 0 (silence now, not a guarantee later)
check 26/33: the client's entry for web2 now points at the intruder: unauthenticated, last writer wins
  | 198.18.6.11 dev eth0 lladdr 02:00:00:00:06:66 STALE

```

`arping` (without `-D`) to an address is the fastest IP-conflict test there is: two different MACs answering one request is proof. `arping -D` sends the RFC 5227 probe from 0.0.0.0, so it can be run before an address is configured; its exit status is 1 when someone answers. The intruder could only poison the client's entry for 198.18.6.11 because the client already had one — exactly why real attacks target the gateway.

```
check 30/33: a Calico-style pod: its gateway 169.254.1.1 exists nowhere; the node answers by proxy ARP
```

## Real-World Troubleshooting Scenario

### Scenario: "Half Our Servers Went Offline After a Load Balancer Failover"

**The situation:**

A company runs a pair of HAProxy load balancers in active/passive configuration using keepalived. The virtual IP (VIP) is `10.0.5.100`, which clients connect to for all API traffic. The primary LB fails at 2:00 AM. Keepalived on the secondary detects the failure and takes over the VIP within 2 seconds. The secondary LB is healthy, all backend servers are healthy, but 40% of clients continue to get connection timeouts for the next 2–4 minutes. The other 60% failover instantly and work fine.

**Why this happens:**

This synthetic case hypothesizes incomplete neighbor/FDB convergence. Confirm the
VIP's owner and new MAC on the adjacent segment; the percentages do not identify
the cause. The lab shows the mechanism: a Linux neighbor that misses the
announcement keeps the old MAC until its entry ages and three probes fail (up to
~53 s with defaults); routers and other operating systems often keep ARP entries
far longer (minutes to hours), which matches "2–4 minutes" better than any Linux
client would. Two observation points matter:

1. **Clients on the VIP's VLAN:** Their neighbor cache can contain the VIP mapping.
2. **Off-subnet clients:** They resolve their own gateway, not the remote VIP. The
   router adjacent to the VIP owns the relevant VIP neighbor entry. Check that
   entry and switch forwarding state; clients in other VLANs do not retain its MAC.

**How to diagnose this with the tools from this lab:**

**Step 1 — Check the ARP cache on an affected client:**

```bash
# On a client in the VIP's subnet, or the router interface adjacent to the VIP:
ip neigh show | grep 10.0.5.100
# Expected (broken): 10.0.5.100 dev eth0 lladdr aa:aa:aa:aa:aa:aa STALE
#                                                 ↑
#                                           Old primary LB's MAC
# Expected (working): 10.0.5.100 dev eth0 lladdr bb:bb:bb:bb:bb:bb REACHABLE
#                                                  ↑
#                                            New secondary LB's MAC
```

**Step 2 — Check ARP on the router between VLANs:**

```bash
# On the router:
ip neigh show | grep 10.0.5.100
# If this shows the old MAC → the router is sending frames to the dead LB
```

**Step 3 — Force an ARP update:**

```bash
# On the secondary LB: send gratuitous ARP manually
sudo arping -A -c 4 -I eth0 10.0.5.100

# On the router: flush the ARP entry
sudo ip neigh flush 10.0.5.100 dev eth0
# Then ping to re-resolve
ping -c 1 10.0.5.100
```

**Step 4 — Long-term fix:**

- Configure keepalived to send gratuitous ARPs multiple times (`vrrp_garp_master_repeat 5`) and with a delay between them (`vrrp_garp_master_delay 1`).
- Verify announcements are received and accepted under the router's documented
  neighbor policy. Do not shorten cache aging below failover detection as a generic fix.
- If clients are on multiple VLANs, the router between VLANs must receive and process the gratuitous ARP. Verify the router is on the same broadcast domain as the VIP.
- If this pair runs in a cloud VPC, none of the above applies: gratuitous ARP cannot move the VIP there. keepalived needs a `notify_master` script that reassigns the IP or updates the route table through the provider's API (6.5).

**Step 5 — Capture evidence for the post-mortem:**

```bash
# Capture ARP traffic during a planned failover test
sudo tcpdump -i eth0 -nn -e -w /tmp/failover-arp.pcap arp

# Trigger failover, then analyze:
sudo tcpdump -nn -e -r /tmp/failover-arp.pcap
# Verify: do you see the gratuitous ARP? Is it broadcast? Does it contain the new MAC?
```

| Symptom                                                | ARP-Related Cause                                             | How to Confirm                                                     | Fix                                                          |
| ------------------------------------------------------ | ------------------------------------------------------------- | ------------------------------------------------------------------ | ------------------------------------------------------------ |
| Ping to local host fails, FAILED in `ip neigh`         | Host is down, wrong VLAN, or cable issue                      | `arping -I eth0 <IP>` — no reply                                   | Check target is up, same VLAN, cable connected               |
| Intermittent connectivity to gateway                   | ARP cache flipping between two MACs (IP conflict or spoofing) | `tcpdump arp` — watch for two different MACs answering the same IP | Find and remove the duplicate IP, enable DAI                 |
| Failover takes minutes instead of seconds              | Gratuitous ARP not reaching all clients                       | `ip neigh show` on affected clients — stale old MAC                | Send gratuitous ARP, configure repeat count in keepalived    |
| Container can't reach another container on same bridge | ARP not resolving across bridge, or namespace issue           | `ip neigh show` inside container — FAILED state                    | Check bridge connectivity, veth pair status                  |
| VIP failover works on-premises, not in the cloud       | The provider owns IP-to-NIC mapping; gratuitous ARP is ignored | VIP still attached to the old NIC in the console/API              | Move the IP or route through the provider API on takeover    |
| Pod can't reach anything; `169.254.1.1 FAILED` in pod  | Node-side veth lost `proxy_arp` or its route to the pod (Calico) | `sysctl net.ipv4.conf.cali….proxy_arp` and `ip route` on the node | Restore the CNI's interface config (restart the CNI agent)   |
| First packet to a new neighbor takes ~0.1–0.8 s        | Proxy ARP reply delayed by `proxy_delay`                       | Capture: request-to-reply gap on the proxy interface               | Set `proxy_delay=0` on proxying interfaces                   |
| Traffic going to wrong host                            | ARP spoofing or IP conflict                                   | `arp -n` shows wrong MAC for a known IP                            | Find the rogue device, add static ARP entry for critical IPs |
| "No route to host" after ~3 s, but a route exists      | ARP resolution fails for the next hop (gateway or on-link host) | `ip neigh show` — entry FAILED; capture shows 3 unanswered requests | Check L2 connectivity, VLAN, and the target's address/mask   |

## Summary

- ARP maps IP addresses (Layer 3) to MAC addresses (Layer 2). It is needed because Ethernet frames are addressed by MAC, not by IP. Without ARP, local network communication is impossible.
- ARP uses broadcast requests and unicast replies. Every host on the segment receives the request; only the target responds. This means ARP traffic is confined to the broadcast domain.
- The ARP cache stores resolved IP-to-MAC mappings. Key states: REACHABLE (confirmed valid), STALE (not recently confirmed), FAILED (resolution failed — Layer 2 connectivity problem).
- Linux timers decide how long a wrong mapping survives: REACHABLE for 15–45 s, DELAY 5 s, three unicast probes 1 s apart. A missing neighbor fails in about 3 s ("Destination Host Unreachable" from your own IP, or EHOSTUNREACH). An unannounced move takes up to ~53 s to heal; the lab measured 12–21 s with a shortened timer.
- Gratuitous ARP is an unsolicited announcement of an IP-to-MAC mapping. It updates entries neighbors already have (it does not create new ones by default) and turns that outage into none. keepalived, VRRP, MetalLB's Layer 2 mode, and active/passive load balancers depend on it — and it does nothing in a cloud VPC, where failover is an API call.
- Proxy ARP lets a host answer for addresses it routes. Calico uses it to give every pod the gateway 169.254.1.1.
- ARP has no authentication. Any host can claim any IP. ARP spoofing enables man-in-the-middle attacks on the local segment. Defenses include Dynamic ARP Inspection (DAI), static ARP entries for critical hosts, and 802.1X.
- Cloud neighbor resolution is provider-specific; guest-created bridge/overlay
  segments still need independent analysis. Correct TLS protects authenticated
  content, not availability, against traffic redirection.
- When you see FAILED in `ip neigh show`, nothing answered at Layer 2. Check that the target really has that address (and a matching mask), then VLAN configuration, switch port state, and physical connectivity — not DNS. An arping to the address is the quickest test; two answers mean an IP conflict.

```
MODULE 6: ARP — ADDRESS RESOLUTION PROTOCOL — QUICK REFERENCE
═══════════════════════════════════════════════════════════════

WHAT ARP DOES
  Maps IPv4 address → MAC address on the local network.
  Required because Ethernet frames use MAC addresses, not IP.

ARP PROCESS
  1. Check ARP cache → if hit, use cached MAC
  2. Send ARP Request (broadcast ff:ff:ff:ff:ff:ff): "Who has <IP>?"
  3. Target responds with ARP Reply (unicast): "<IP> is at <MAC>"
  4. Cache the result

ARP CACHE STATES (Linux timers in brackets)
  REACHABLE    Recently confirmed — valid, use directly [15–45 s]
  STALE        Not recently confirmed — will re-verify on next use
  DELAY        Sent traffic, waiting briefly for confirmation [5 s]
  PROBE        Actively sending unicast ARP to re-verify [3 × 1 s]
  FAILED       No response — host unreachable at Layer 2 [after 3 × 1 s]
  INCOMPLETE   ARP request sent, waiting for reply
  PERMANENT    Static entry — never expires, never overwritten

ESSENTIAL COMMANDS
  ip neigh show                   View ARP cache (all entries)
  ip neigh show dev eth0          View ARP cache for one interface
  arp -n                          Legacy ARP cache view
  sudo ip neigh flush dev eth0    Flush ARP cache for interface
  sudo arping -I eth0 <IP>       Send ARP request and show reply
  sudo arping -A -c 1 -I eth0 <IP>  Send gratuitous ARP (reply form)
  sudo arping -U -c 1 -I eth0 <IP>  Send gratuitous ARP (request form)
  sudo arping -D -c 2 -I eth0 <IP>  Duplicate address detection (exit 1 = taken)
  sudo tcpdump -i eth0 -nn -e arp   Capture ARP traffic with MAC headers
  ip -s neigh show <IP>           Ages: used/confirmed/updated seconds
  (arping flags above are iputils-arping; the "arping" package differs)

KERNEL KNOBS (net.ipv4.conf.<if>.*)
  arp_accept=0   Announcements update existing entries, never create new ones
  arp_notify=0   No announcement on MAC change unless set to 1
  proxy_arp=0    Answer for routed addresses only if set to 1
  (neigh.<if>.proxy_delay = up to 0.8 s before a proxy reply; 0 for CNIs)

GRATUITOUS ARP
  Unsolicited ARP where sender IP == target IP.
  Used for: failover (VIP takeover), IP conflict detection, announce new MAC.
  Linux does NOT send one when an address is added; failover tools do.
  Identifier in capture: "who-has X tell X" or "Reply X is-at ..."
  where X is the sender's own IP.

KEY SIGNALS
  ip neigh FAILED             Layer 2 problem — host unreachable locally
  ip neigh STALE              Entry aging — will re-verify when needed
  Two MACs for same IP        IP conflict or ARP spoofing
  Gratuitous ARP in capture   Failover event or IP reconfiguration

ARP vs CLOUD
  Physical network    Standard ARP — broadcast on shared segment
  Cloud VPC           Provider answers ARP — no broadcast to other VMs
                      Azure: every IP → 12:34:56:78:9a:bc; GCP Linux: /32, gateway only
```
